### 2.1 유지보수 대상 자산 분류

AgenticWorkflow 하네스의 유지보수 범위를 **정적 자산**과 **동적 자산**으로 분리한다.

**정적 자산** (변동 빈도 낮음):
- `CLAUDE.md`, `AGENTS.md`, `soul.md`, `DECISION-LOG.md`: 프로젝트 헌법. 분기 단위 업데이트.
- `docs/protocols/*.md`: autopilot·quality-gates·ulw·context-preservation·code-change. 월 1-2회 수정.
- `.claude/settings.json`: Hook 등록. 신규 Hook 추가 시만.

**동적 자산** (변동 빈도 높음):
- `.claude/hooks/scripts/*.py` (21개+ 스크립트): Claude Code 업데이트·신규 규칙 추가 시 수정.
- `.claude/agents/*.md` (translator·reviewer·fact-checker): 도메인 확장·프롬프트 튜닝.
- `.claude/commands/*.md` (/install·/maintenance): 워크플로우 진화에 따라.
- `.claude/skills/workflow-generator/`, `doctoral-writing/`: 스킬 자체 진화.
- `translations/glossary.yaml`: 번역 용어 누적.
- `prompt/`, `coding-resource/`: 프로젝트 자료.

### 2.3 디버깅 부담 패턴

Hook 시스템·Sub-agent·병렬 실행이 얽히면 디버깅 난이도가 급상승한다. 실제 관찰된 패턴:

**패턴 1 — Hook silent failure**:
- `generate_context_summary.py` 등 Stop/SessionEnd hook은 stdout/stderr가 유저에게 노출되지 않음.
- 증상: 스냅샷 파일이 생성되지 않거나 오래된 상태.
- 디버깅: `.claude/hooks/logs/` (있다면) 확인 → `stderr | tee`로 수동 로그 주입 → 직접 실행.
- 평균 해결 시간: 1-3시간.

**패턴 2 — validate_*.py 규칙 충돌**:
- `validate_pacs.py` PA3가 `validate_review.py` R2와 상호 의존할 때, 한쪽 스키마 변경 시 체인 실패.
- 증상: 특정 작업 단계에서 모호한 exit 2.
- 디버깅: 스크립트별 단독 실행 + 입력 재현.
- 평균 해결 시간: 2-5시간.

**패턴 3 — 컨텍스트 복원 실패**:
- `restore_context.py`가 RLM 인덱스 손상 시 복원 무효화.
- 증상: `[CONTEXT RECOVERY]` 표시는 있으나 내용이 비어 있음.
- 디버깅: `.claude/context-snapshots/knowledge-index.jsonl` 수동 검증.
- 평균 해결 시간: 30분-2시간.

**패턴 4 — 병렬 Task 도구 결과 병합 오류**:
- 5-10 Sub-agent 결과를 Orchestrator가 병합할 때 일부 누락.
- 증상: summary/index 파일에 일부 teammate 결과가 빠짐.
- 디버깅: 개별 Task 결과를 원천에서 재확인.
- 평균 해결 시간: 1-2시간.

**패턴 5 — `update_work_log.py` 9-도구 필터 drift**:
- Claude Code 신규 도구 추가 시 work log 누락.
- 증상: PostToolUse에서 특정 도구 이벤트가 기록되지 않음.
- 평균 해결 시간: 30분-1시간.

### 2.4 버전 드리프트 리스크

- **Claude Code 업데이트 주기**: 약 2-4주. minor 업데이트마다 Hook signature·도구 목록·권한 모델 미세 변경 가능.
- **드리프트 발생 지점**:
  - `settings.json` hook 이벤트명 변경 → 모든 hook 무효화 리스크.
  - 새 built-in 도구 추가 → `update_work_log.py` 필터 누락.
  - Task tool 병렬 상한 정책 변경 → 워크플로우 병렬도 재조정 필요.
  - MCP 서버 spec 변경 → `mcp__github__*` 도구 이름 변경.
- **대응 전략**:
  - `setup_maintenance.py`를 주 1회 자동 실행하여 드리프트 조기 감지.
  - Claude Code CHANGELOG 모니터링 (공식 docs + `/help`).
  - `/install` 명령으로 setup-init 검증 주기화.

## §4. 과금 모델 비교 (Pricing Model Comparison)

### 4.1 주요 과금 모델 유형

**모델 A — Pure Freemium Subscription**:
- Free tier(제한적) + Premium 월/연 구독.
- 예시: Lasting(월 $11.99), Paired(월 $9.99, 연 $29.99), Replika(월 $9.99).
- 장점: 유저 불안 최소 (정액제) · 예측 가능 매출.
- 단점: 무료 유저가 비용 유발 (Branch B일 때 특히 심각).

**모델 B — Usage-Based (토큰·세션)**:
- 세션당 결제 또는 월 토큰팩 충전.
- 예시: OpenAI API, Character.ai 일부 tier.
- 장점: 매출-비용 선형 일치.
- 단점: **관계 위기 순간의 과금 불안** → Replika 2023 이탈 선례 (D-4 참조).
- **본 프로젝트 적용 불가** (B2C 금지).

**모델 C — Hybrid Freemium + Token Pack**:
- Free + Premium 구독 + 옵션 토큰팩(장시간 세션·전문가 매칭).
- 예시: Wysa (구독 + therapist add-on).
- 장점: 가벼운 유저는 구독, 헤비유저는 토큰팩.
- 단점: 복잡도 증가 · UX 커뮤니케이션 난이도.

**모델 D — One-time Purchase + In-App**:
- 앱 구매 후 개별 콘텐츠 결제.
- 예시: Gottman Card Decks, Love Nudge 일부.
- 장점: 부담 없는 진입.
- 단점: 지속 매출 어려움.

**모델 E — B2B SaaS (조직 계약)**:
- 회사·EAP(Employee Assistance Program)·건강보험사가 구독.
- 예시: Ginger, Lyra Health.
- 장점: ARPU 매우 높음, 이탈률 낮음.
- 단점: Sales cycle 길고, B2C 플라이휠 약함.

## §8. 데이터 거버넌스 (Data Governance)

### 8.1 데이터 분류 체계

**Class 1 — 로컬 온디바이스 전용 (Never Leaves Device)**:
- 관계 갈등 대화 원문.
- 감정 일기·진단 결과.
- 파트너·제3자 실명 멘션.
- → Branch A 기본, Hybrid Tier 1에서도 유지.

**Class 2 — 동의 기반 클라우드 처리 (With Consent)**:
- 통계 집계된 증상 패턴 (가명화).
- Tier 2 Sonnet 호출 시 전송되는 발췌 대화 (mini-context).
- Tier 3 Opus + 전문가 매칭 시 전문가에게 공유되는 대화.

**Class 3 — 공개 데이터 (Public)**:
- 유저 동의 후 공유되는 블로그·커뮤니티 포스트 (실명 마스킹).
- 익명화된 FAQ 사례.

**Class 4 — 운영 데이터 (Operational)**:
- 구독·결제 정보.
- 크래시 리포트.
- 사용 패턴 analytics (프라이버시 보호 방식).

### 8.2 데이터 흐름 설계 원칙

**P-D1. Data Minimization (최소화)**:
- Tier 2 클라우드 호출 시 최근 N턴만 전송 (예: 최근 5턴).
- 사용자 식별 정보(이름·전화)는 절대 서버로 보내지 않음.
- 세션 ID는 랜덤 UUID, 변경 가능.

**P-D2. Purpose Limitation (목적 제한)**:
- 수집 목적 외 활용 금지 (PIPA 제18, GDPR Art. 5(1)(b)).
- 광고 타겟팅 금지 명시.

**P-D3. Storage Limitation (저장 기간)**:
- 로컬: 유저 제어 (기본 90일 rolling, 옵션으로 무기한).
- 클라우드 Tier 2: 호출 직후 삭제 (세션 히스토리 재구성 불가).
- 클라우드 Tier 3 (전문가 매칭): 법정 보관 5년 (상담 기록).
- 결제: 전자상거래법 5년.

**P-D4. Transparency (투명성)**:
- 실시간 데이터 흐름 시각화 (어디로 가는지 유저에게 보임).
- "이 메시지는 기기 내에서만 처리됩니다" / "서버로 전송됩니다" 라벨.

**P-D5. User Control (유저 통제)**:
- 전체 데이터 내보내기 (PIPA 제38, GDPR Art. 20).
- 전체 데이터 삭제 (PIPA 제36, GDPR Art. 17).
- 개별 항목 삭제 (대화 단위).

**P-D6. Security by Design (보안)**:
- 로컬: 앱 샌드박스 + 기기 암호화 (iOS Data Protection API·Android Keystore).
- 클라우드: TLS 1.3 전송 + AES-256 저장 암호화.
- 비밀번호: Argon2 / scrypt.
- API key: 환경 변수 + 로테이션.

**P-D7. Accountability (책임)**:
- DPO 지정 (5인 이상 조직 권장).
- DPIA 실시 (민감정보 처리).
- 처리 활동 기록 (Art. 30).
- 침해 대응 플랜 (72시간 통지).

### 8.3 국외이전 대응 프로토콜 (PIPA 제28조의9)

Tier 2 Sonnet / Tier 3 Opus 클라우드 호출 시:

1. **동의 UI**:
   - 첫 사용 시 별도 동의 화면 (일반 약관과 분리).
   - 수탁자명 (Anthropic), 국가(미국), 처리 목적, 보유 기간, 거부 권리 명시.
   - 동의 기록 타임스탬프·IP 저장.

2. **동의 거부 시 fallback**:
   - Tier 1 로컬로만 작동.
   - 기능 제한 안내 (숨기지 않음).

3. **DPIA (Data Protection Impact Assessment)**:
   - Branch B·Hybrid Tier 2+3 출시 전 필수.
   - 개인정보보호위원회 권고 템플릿 활용.

4. **표준계약조항 (SCCs)**:
   - Anthropic DPA 검토·서명.
   - EU 확장 시 추가 SCCs.

### 8.4 데이터 내보내기·삭제 기술 구현

**Export (이동권)**:
- JSON / CSV / PDF 형식.
- 대화 원문·감정 일기·진단 결과 모두 포함.
- 7일 이내 제공 (GDPR 30일 한도 대비 여유).

**Delete (삭제권)**:
- 즉시 로컬 삭제.
- 클라우드: 30일 이내 완전 삭제 (백업 포함).
- Tier 3 전문가 매칭 기록: 상담 기록 보관 의무 있을 경우 익명화 후 보존 (유저 고지).

**Audit Trail**:
- Export·Delete 요청 로그 5년 보관 (법적 분쟁 대비).

### 8.5 학습 데이터 거버넌스

- **원칙**: 유저 대화는 **기본적으로 LLM 학습에 사용하지 않음** (Anthropic DPA 확인 + 자체 정책 명시).
- **옵트인 연구 기여 프로그램**:
  - 명시적 opt-in (default opt-out).
  - 가명화 + 맥락 재구성 불가 수준 익명화.
  - 보상 제공 (구독 1개월 무료 등).
  - 학술 공개 시 윤리위원회 검토.
- **합성 데이터 우선**: 자체 개선은 합성 대화 생성기 기반 (D-7 원칙).

### 8.6 침해 대응 플레이북

**단계 0 — 탐지**:
- 모니터링 (비정상 DB 접근·대량 다운로드).
- 유저 제보 채널.

**단계 1 — 봉쇄 (0-4시간)**:
- 영향 범위 파악.
- 시스템 격리.
- 접근 권한 로테이션.

**단계 2 — 통지 (4-72시간)**:
- 개인정보보호위원회 (PIPA).
- DPA (GDPR, EU 유저 있는 경우).
- 영향 유저.
- 언론 (공개 필요 시).

**단계 3 — 복구 (72시간-30일)**:
- 취약점 패치.
- 보안 감사.
- 재발 방지 대책.

**단계 4 — 사후 (30일+)**:
- 공식 사고 보고서.
- 유저 신뢰 회복 (보상·transparency 강화).

### 8.7 데이터 거버넌스 종합 판정

- **Branch A 우선의 거버넌스 이점**: Class 1 데이터가 기기 내에 머무름 → 침해 표면 최소.
- **3-tier Hybrid의 거버넌스 정당성**: Tier별 데이터 분류 명확, 유저 동의 단계 분리 가능.
- **핵심 차별화**: "데이터 흐름 시각화" (P-D4)는 마케팅 자산 — BetterHelp 대비 신뢰 해자.
- **운영 부담**: DPO·DPIA·SCCs 행정 부담이 있으나 Branch A 기본이면 최소화 가능.

## §9. 확장 한계 — B2C → B2B·다언어 (Expansion Limits)

### 9.1 B2C → B2B 확장 경로

**B2B 유망 시장**:
- **EAP (Employee Assistance Program)**: 한국 삼성·SK·LG 등 대기업 직원 복지.
- **건강보험사**: 예방·웰니스 프로그램.
- **결혼 준비 업체**: 웨딩홀·혼수·웨딩플래너 번들.
- **교육기관·종교기관**: 부부·가족 프로그램.
- **정부·지자체**: 가족상담센터 파트너십.

**B2C → B2B 전환 시 필수 기능**:

| 기능 | B2C | B2B 추가 |
|---|---|---|
| 인증 | 이메일/SNS | SSO (SAML·OIDC·Active Directory) |
| 요금제 | 개인 구독 | 조직 계약·시트 기반 |
| 권한 | 개인 | 관리자·일반·게스트 roles |
| 감사 로그 | 최소 | 상세 (SOC 2·ISO 27001) |
| 데이터 격리 | 단일 테넌트 | 멀티 테넌트 격리 |
| 결제 | Stripe·인앱결제 | 인보이스·PO |
| 지원 | Email·Chat | 계약 SLA·전담 CS |
| 커스텀 | 없음 | 로고·브랜딩·커스텀 도메인 |

**Branch A vs Branch B의 B2B 적합성**:
- **Branch A pure**: B2B 기업 관리자 대시보드·감사 로그 어려움 (로컬 앱이라 중앙 수집 제한).
- **Branch B**: B2B 친화적 구조.
- **3-tier Hybrid**: Class 4 운영 데이터만 서버 수집으로 B2B 대응 가능.

### 9.2 B2B 확장 시 기술 부담

- **단일 테넌트 → 멀티 테넌트**: 재설계 필수. Phase 1 설계 시 테넌시 추상화 필요.
- **SSO 통합**: Okta·Azure AD·Google Workspace. 분기 단위 엔지니어링 투자.
- **컴플라이언스**: SOC 2 Type II 인증 (3-6개월·2-5천만원), ISO 27001 (6-12개월·5천만-1억원).
- **B2B 세일즈 사이클**: 3-9개월. CEO·CHRO·복지팀·법무팀 다단계 의사결정.
- **계약 법무**: MSA·DPA·SCCs·BAA 각 계약 분기별 갱신.

### 9.3 다언어 확장 경로

**확장 우선순위** (시장 크기 + 규제 난이도 + 한국 근접성):

| 언어·시장 | 우선순위 | 시장 특성 | 규제 |
|---|---|---|---|
| 영어 (US) | ★★★★☆ | 거대 시장·경쟁 포화 | HIPAA·주별 |
| 일본어 (JP) | ★★★★★ | 한국 유사 문화·고부·직장 문제 공통 | 개인정보보호법 엄격 |
| 중국어 번체 (TW) | ★★★★☆ | 관계 문화 유사·시장 중간 | PDPA |
| 영어 (EU) | ★★★☆☆ | 시장 다양·규제 어려움 | GDPR 매우 엄격 |
| 베트남어·태국어 | ★★★☆☆ | 한류·신흥 시장 | 국가별 상이 |
| 중국어 간체 (CN) | ★☆☆☆☆ | 거대 시장이나 규제 극단적 | CSL·PIPL·DSL |

**다언어 확장 시 코스트**:

- **번역**: 전문가 번역 + 현지 검수 (단순 AI 번역 불가 — 관계 뉘앙스).
- **문화 현지화**: 일본 "혼기"·중화권 "장자 부담"·유럽 "자율성" 등 관계 규범 차이.
- **LLM 모델**: 언어별 튜닝 필요 (EXAONE은 한국어 최적, 일본어는 다른 모델).
- **규제**: 국가별 대응 (GDPR·PIPL 등).
- **결제**: 현지 결제 수단 (중국 WeChat Pay·일본 편의점 결제 등).
- **고객 지원**: 현지 언어 CS 인력.

### 9.4 확장 시 LLM 모델 전략

- **한국어**: EXAONE 3.5 (Branch A) / Claude Sonnet (Branch B).
- **일본어**: Claude Sonnet 우수 / 로컬은 Swallow·ELYZA.
- **영어**: Claude 전 모델 우수 / 로컬은 Llama 3.1.
- **중화권**: Qwen·Yi 계열 / 클라우드는 GPT-4o.
- **다국어 동시 지원 앱 크기**: Branch A의 경우 모델 여러 개 내장 불가 → 언어별 별도 빌드 or 동적 다운로드.

### 9.5 확장 limiting factors (병목)

- **L-1. 인력**: 1인 → 5인 전환이 가장 큰 허들. 특히 현지화 PM.
- **L-2. 법무**: 국가별 법률 자문 연간 수천만원 규모.
- **L-3. 모델 품질**: 한국어 외 언어 로컬 LLM 품질이 확장 속도 제약.
- **L-4. 컴플라이언스**: SOC 2·GDPR DPIA 등 시간 소모.
- **L-5. 브랜드**: 신뢰 기반 카테고리라 브랜드 이식이 어려움.

### 9.6 확장 권장 경로 (Phase별)

**Phase 1 (0-12개월)**: 한국 B2C 집중.
**Phase 2 (12-24개월)**: 일본 진출 (문화·시장·한국 LLM 기술 이전 가능성). 한국 B2B 동시 개발.
**Phase 3 (24-36개월)**: 영어권 B2C + 한국 B2B EAP 본격화.
**Phase 4 (36개월+)**: 중화권·EU 선택적 진출.

### 9.7 확장 한계 종합 판정

- **B2B는 Phase 3 최단 경로 + 기술 재설계 비용**.
- **다언어는 일본어 우선이 ROI 최고**.
- **Branch A pure는 B2B 확장 구조적 약함** → Hybrid Tier 구조가 양립 가능.
- **확장 타이밍**: B2C에서 MAU 10만+ 도달 후 B2B 병행이 안전.
